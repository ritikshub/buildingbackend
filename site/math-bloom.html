Bloom filters and HyperLogLog: a billion things in 12 KB

A Bloom filter answers "have I seen this before" with about ten bits per item and never says no when the answer is yes. HyperLogLog counts how many different things went past using twelve kilobytes, whether that is a thousand or a billion. Both cheat the same way: keep a fingerprint of the data instead of the data, and know exactly what the cheat costs.

Plain text is theory. Boxed examples: problem, working, answer.

Where you meet it

Both structures live wherever the real data is too big or too slow to touch on every request.

Every database that writes to files

RocksDB, Cassandra and their relatives keep a Bloom filter per file so a lookup for a missing key skips the disk entirely. Example 3 prices the filter: 125 MB to guard 100 million keys.

Every git log -- file

git stores a Bloom filter of the paths each commit touched, so history for one file skips most commits without opening them. "Use it" reads git's own count of hits, misses and false positives in this repository.

Every unique-visitor number

Daily active users, distinct IPs, unique search queries. Redis answers PFCOUNT from 12 KB no matter how many you add. Examples 5 and 6 build the estimate from eight registers up to Redis's 16,384.

Every join planner and cache

SQLite builds a Bloom filter of one table before probing another with it, and caches ask a filter before paying for a lookup. Example 2 is the formula both of them are sized with.

The idea in one breath

A Bloom filter is a row of m bits, all zero to start, plus k hash functions. To add an item, hash it k ways and set those k bits to one. To ask about an item, hash it the same k ways and look: if any bit is still zero the item was definitely never added, because adding it would have set that bit. If all k bits are one it was probably added, but other items may have set those bits between them. That "probably" is a false positive, and its rate is a number you choose by choosing m and k.

HyperLogLog counts distinct items without remembering any of them. Hash each item to a long random-looking string of bits and look at how many zeros it starts with. Half of all hashes start with a one; a quarter start with exactly one zero; one in a billion starts with thirty zeros. So if the longest run you have seen is thirty, you have probably seen about a billion different things. Duplicates hash to the same bits, so they change nothing, which is the whole point.

One longest run is a terrible estimate: a single unlucky hash doubles it. So the hash's first few bits pick one of m registers, each register keeps its own longest run, and the m estimates are averaged with a harmonic mean, which refuses to be dragged up by one outlier. The error falls as 1.04/√m: with 16,384 registers of 6 bits each, 12 KB, it is 0.81%.

A Bloom filter by hand

The filter is right about PIG and FOX and wrong about ACT, which was never added: a false positive. One zero bit is enough to say no with certainty, because adding ACT would have set it. Two ones are never enough to say yes, because CAT and HEN may have set them. That asymmetry is the whole contract: no false negatives, ever, and a false-positive rate you can compute.

How wrong, exactly

After n items and k hashes each, kn bits have been set, some more than once. Tool 2 says a given bit is still zero with chance about e−kn/m. A stranger is a false positive when all k of its bits happen to be one:

p ≈ (1 − e−kn/m)k

Two knobs. More bits per item, m/n, always helps. More hashes help until the filter fills up, then hurt; the best k is about 0.7 × m/n. This is the formula from Burton Bloom's 1970 paper, and every database that ships a filter sizes it with this line.

A 1% filter costs about 10 bits per item, with 7 hashes, and that figure does not depend on what the items are. Notice that at the best k roughly half the bits end up set, 0.503 here: the filter is most efficient when it is half full. Doubling the bits to 20 does not halve the error, it divides it by about a hundred, because the error is an exponential in the bits per item.

Where the bits pay for themselves

A database that writes sorted files (RocksDB, Cassandra, LevelDB and the storage engines built on them) may hold one key in any of ten or more files. Without a filter, a lookup for a key that does not exist has to open every file. With a 10-bit-per-key filter in memory for each file, it opens almost none.

Counting by the longest run of zeros

Now the other question: not "have I seen this" but "how many different ones have I seen". Hash every item and keep only one number, the longest run of leading zeros you have met. Tool 3 says a run of r − 1 zeros before the first one shows up once in 2r hashes, so the longest run you have seen is a rough log of how many distinct items went past. Duplicates produce the same hash and cannot change the maximum.

A billion distinct things compress to the number 30, which is the miracle. The fix is the same as every noisy measurement: take many and average, and average in a way that one outlier cannot hijack.

HyperLogLog by hand

Split the hash. The first b bits choose one of m = 2b registers, and the rest of the bits supply the run of zeros. Each register keeps the largest position it has seen. Then combine them with the harmonic mean from tool 4, scaled by m and by a constant αm that Flajolet and his co-authors computed to cancel the mean's built-in bias:

E = αm × m² / (2−R₁ + 2−R₂ + … + 2−Rm)

One correction: when the estimate is small compared with m (below 2.5m), some registers are still empty and counting those is more accurate: E = m × ln(m / empty).

Feed the same twenty words in again and nothing moves: every register already holds the maximum those hashes can produce. That is why counting duplicates is free.

Buying accuracy with registers

The standard error of the estimate is 1.04/√m: four times the registers halves the error. Each register only needs to hold a position, and positions are small: with 64-bit hashes and 14 bits spent on choosing a register, the longest possible run fits in 6 bits. So the whole structure is m × 6 bits, whatever you count with it.

Run it

Build it: both structures, then the formulas they should match

Standard library only. The filter is a bytearray; the counter is a list of 1,024 small integers. Both use SHA-256 as the source of random-looking bits.

# A Bloom filter and a HyperLogLog, each in a dozen lines, checked against
# their formulas. Companion to math-bloom.html. Python 3 stdlib only.
import hashlib, math, random

def hashes(item, k, m):
    """k bit positions in 0..m-1, carved out of one SHA-256."""
    h = hashlib.sha256(item.encode()).digest()
    return [int.from_bytes(h[4*i:4*i+4], "big") % m for i in range(k)]

def bloom_test(n, bits_per_item, k, trials=100_000):
    m = n * bits_per_item
    bits = bytearray(m)
    for i in range(n):
        for p in hashes(f"user:{i}", k, m): bits[p] = 1
    false = sum(all(bits[p] for p in hashes(f"stranger:{j}", k, m)) for j in range(trials))
    formula = (1 - math.exp(-k * n / m)) ** k
    return 100 * false / trials, 100 * formula

print("Bloom filter: 100,000 items in the filter, 100,000 strangers queried")
print("bits/item  k   measured  formula   (false positives, %)")
for bpi, k in ((8, 6), (10, 7), (16, 11)):
    meas, form = bloom_test(100_000, bpi, k)
    print(f"{bpi:8d}  {k:2d}   {meas:6.3f}%   {form:6.3f}%")

def hll_count(items, p=10):
    """HyperLogLog with m = 2^p registers: bucket by the top p bits of the
    hash, keep the longest run of leading zeros seen in the rest."""
    m = 1 << p
    regs = [0] * m
    for item in items:
        x = int.from_bytes(hashlib.sha256(item.encode()).digest()[:8], "big")   # 64 bits
        bucket, rest = x >> (64 - p), x & ((1 << (64 - p)) - 1)
        rho = (64 - p) - rest.bit_length() + 1             # position of the first 1 bit
        regs[bucket] = max(regs[bucket], rho)
    alpha = 0.7213 / (1 + 1.079 / m)
    est = alpha * m * m / sum(2.0 ** -r for r in regs)
    zeros = regs.count(0)
    if est < 2.5 * m and zeros:                            # small-range correction
        est = m * math.log(m / zeros)
    return est

print("\nHyperLogLog with 1,024 registers (1,024 x 6 bits = 768 bytes), error should be about 1.04/sqrt(1024) = 3.25%")
for n in (1_000, 100_000, 1_000_000):
    items = (f"user:{i}" for i in range(n))
    est = hll_count(items)
    print(f"true {n:>9,}   estimate {est:>12,.0f}   off by {100 * (est - n) / n:+.2f}%")

Toy vs production

The structures on this page are the real ones. Production changes the hash, the sizing, and what happens at the edges.

This pageReal systems
hash functionsletter sums; SHA-256 sliced upFast non-cryptographic hashes: MurmurHash3, xxHash. Seven hashes are rarely computed seven times: two hashes a and b give a + i·b for i = 1…k, the double-hashing trick git uses with two murmur3 seeds.
sizing a filter16 bits, fixedSized from the expected item count and a target rate: RocksDB's bits_per_key, Cassandra's bloom_filter_fp_chance (0.01 by default). One filter per immutable file, rebuilt when the file is, so Example 3's overfilled filter never happens.
deletingimpossibleStill impossible: clearing CAT's bits would also delete HEN. Counting Bloom filters keep a small counter per position instead of a bit; cuckoo filters store fingerprints and can delete. Or rebuild the filter, which is what file-based stores do anyway.
registers8, in a list16,384 six-bit registers packed into 12 KB. Redis keeps a sparse encoding while the count is small and switches to the dense one later, so an empty counter does not cost 12 KB.
the estimateαm, one small-range correction64-bit hashes and an empirical bias correction for medium counts, from Google's 2013 "HyperLogLog in practice", which is what most implementations follow. The 1.04/√m error stays.
combiningOR the bits; max the registersExactly that, at scale: PFMERGE unions counters from many servers or many days without error. Intersections are not available directly; inclusion-exclusion on the unions gives one, with the errors adding up.
what you get back"maybe" or "no"; "about 17"Never the items. If you need to list who visited, you need the set. The sketch is for the question you ask a million times a second, and the set is for the report you run once.

Can you remove CAT from the filter in Example 1 by clearing bits 8 and 11?

No. Bit 11 is also HEN's, so HEN would start getting "definitely not" and the filter would have told a lie, the one thing it promises never to do. Bloom filters only grow. To support deletion you keep a small counter in each position instead of a bit and decrement it, at four to eight times the memory, or you rebuild the filter from the data.
