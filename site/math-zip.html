Math Behind Tech · Chapter 02

How zip works

Count the letters, build a tree, and point backwards at things you already said. That is the whole of zip, gzip, PNG and every compressed web page, and you can do all of it with a pencil. At the end we open a real gzip file and read it bit by bit.

Plain text is theory. Boxed examples: problem, working, answer.

Where you meet it

One algorithm, DEFLATE, sits inside all of these. Only the wrapper around it changes.

Every API response

Content-Encoding: gzip. A JSON array of 1,000 small objects is 20,891 bytes on the server and 2,362 bytes on the wire. Example 5 shows why JSON shrinks so well.

Docker images and npm

Every image layer you pull is a tar.gz. Every npm package is a .tgz. Example 10 shows why they are tar.gz and not zip, with a 4× difference on the same files.

Files that are secretly zips

.docx, .xlsx, .jar and .apk are zip archives with a different extension. Rename one and open it. PNG images carry the same DEFLATE stream inside.

Your git repository

Every object in .git/objects is DEFLATE-compressed with a two-byte zlib header. The bytes in Example 8 are what git writes to disk.

The idea in one breath

A file is a row of bytes, 8 bits each, and the 8 is fixed no matter what. An e costs the same as a Z. The fiftieth copy of "ok":true costs the same as the first. Compression is the observation that both of those are wasteful, and it fixes them with two tricks.

Trick one, Huffman coding (1952): give frequent symbols short codes and rare symbols long ones, arranged so that no code is the beginning of another. Trick two, LZ77 (1977): when text repeats, do not write it again. Write "go back 19 characters and copy 11".

DEFLATE (1996) does trick two first, then trick one on the result. zip, gzip, zlib and PNG are DEFLATE with different headers stapled on. That is why one chapter covers all of them.

The four tools you need

Nothing below needs more than these four ideas.

4. Binary trees

A tree where every branch is a bit, 0 for left and 1 for right, and every symbol sits on a leaf. The path from the root to a leaf is that symbol's code. Because a leaf has no children, no path can be the start of another: a tree is automatically prefix-free.

Path: right, right, left
1, 1, 0
code 110

Trick one: spend fewer bits on common letters

Huffman's algorithm builds the tree from the bottom. Count each symbol. Take the two lightest nodes, join them under a new node whose weight is their sum, and put it back. Repeat until one node is left. Rare symbols get merged early and end up deep in the tree with long codes. Common symbols get merged last and stay near the root.

No code with one codeword per letter can beat 22.4 bits. Huffman's 23 is within one bit of perfect. The same formula explains why a JPEG or a random file will not compress: their entropy is already close to 8 bits per byte, so there is nothing to save.

Trick two: point backwards

Huffman looks at one symbol at a time. It cannot see that "ok":true appeared twenty characters ago. LZ77 can. It slides a window over the text, 32 KB wide in DEFLATE, and at every position asks: does the text that comes next already appear somewhere in the window? If it finds a match of at least 3 characters, it writes a copy token, ⟨length, distance⟩, instead of the characters. The decoder just copies. Decompressing is far faster than compressing for exactly this reason: copying is cheap, searching is not.

Putting it together: DEFLATE

DEFLATE runs LZ77 and then Huffman-codes what comes out. The output of LZ77 is a mix of literals and copy tokens, so DEFLATE uses one alphabet for "literal or length" with 286 symbols: 0 to 255 are the byte values, 256 means end of block, and 257 to 285 mean "a copy of length 3 to 258 follows". A second, smaller Huffman tree codes the distances, 1 to 32,768, in 30 buckets.

The stream is cut into blocks. Every block starts with three bits: one that says whether this is the last block, and two that say which trees to use: 00 for none (stored as is), 01 for a fixed pair of trees written into the spec, 10 for trees custom-built for this block and sent at its start. Custom trees are the interesting case: how do you send a tree cheaply?

Example 6

Ship the whole tree as five small numbers

The decoder needs our tree. Sending every code would be expensive. DEFLATE's trick: send only each symbol's code length (A 1, B 3, C 3, D 3, R 3) and let both sides rebuild the codes by one fixed rule: shorter codes first, alphabetical within a length, counting upwards.

Five small numbers rebuild a prefix-free code that costs exactly the same 23 bits. The codes differ from Example 2 (C was 100 there, B is 100 here), and that is fine: only the lengths affect the size. This is called a canonical Huffman code, and it is precisely how DEFLATE ships its trees. Then it goes one step further and Huffman-codes the list of lengths too. DEFLATE compresses the Huffman tree with another Huffman tree.

11 bytes in, 29 bytes out. Compression made it bigger, because 18 bytes of wrapper is more than the 11 bytes being compressed. This is why web servers have a minimum size below which they do not gzip a response.

Now the interesting 11 bytes. DEFLATE packs bits from the least significant end of each byte, so the first byte 73 = 01110011 is read right to left: the header bits are 1, 1, 0. With so little input, gzip decided custom trees would cost more than they save and used the fixed trees from the spec, where every byte value below 144 is an 8-bit code and the end-of-block symbol is 7 bits.

Inside a .zip file

A zip archive is a list of files, each compressed separately with DEFLATE and preceded by a local header that starts with the bytes 50 4b 03 04, which is "PK" followed by 3 and 4. PK is Phil Katz, who wrote PKZIP in 1989, so every zip file on Earth begins with its author's initials. At the end sits a central directory, one entry per file, also starting with PK, and a final end record, also PK. The central directory is why you can list a zip and extract one file without reading the rest. Compressing each file on its own is the price of that feature, and the price is steep.

Run it

Build it: both tricks in forty lines

Standard library only. The Huffman function returns code lengths and the canonical function turns them into codes, exactly as in Example 6. The LZ77 function is the brute-force version of Example 5.

# The two tricks behind zip, with numbers small enough to check on paper.
# Companion to math-zip.html. Specs: RFC 1951 (DEFLATE), RFC 1952 (gzip).
import heapq, zlib
from collections import Counter

def huffman_lengths(text):
    """Trick one. Merge the two lightest nodes until one is left.
    Returns how many bits each symbol gets (the shape of the tree)."""
    counts = Counter(text)
    heap = [(w, i, [[ch, 0]]) for i, (ch, w) in enumerate(sorted(counts.items()))]
    heapq.heapify(heap)
    order = len(heap)
    while len(heap) > 1:
        w1, _, a = heapq.heappop(heap)
        w2, _, b = heapq.heappop(heap)
        for leaf in a + b:
            leaf[1] += 1                      # one more bit for every symbol underneath
        heapq.heappush(heap, (w1 + w2, order, a + b))
        order += 1
    return dict(heap[0][2])

def canonical(lengths):
    """DEFLATE's rule for turning lengths into codes: shortest first,
    alphabetical within a length, counting upwards."""
    codes, code, prev = {}, 0, 0
    for sym, n in sorted(lengths.items(), key=lambda kv: (kv[1], kv[0])):
        code <<= n - prev
        codes[sym] = format(code, f"0{n}b")
        code, prev = code + 1, n
    return codes

def lz77(text, min_match=3):
    """Trick two. At each position, find the longest earlier copy of what
    comes next. Emit ('copy', length, distance) or ('lit', char)."""
    i, out = 0, []
    while i < len(text):
        best = (0, 0)
        for j in range(i):
            n = 0
            while i + n < len(text) and text[j + n] == text[i + n]:
                n += 1
            if n > best[0]:
                best = (n, i - j)
        if best[0] >= min_match:
            out.append(("copy", best[0], best[1])); i += best[0]
        else:
            out.append(("lit", text[i])); i += 1
    return out

word = "ABRACADABRA"
lengths = huffman_lengths(word)
codes = canonical(lengths)
bits = sum(len(codes[ch]) for ch in word)
print("code lengths", lengths)
print("codes       ", codes)
print("encoded     ", " ".join(codes[ch] for ch in word))
print(f"{len(word) * 8} bits in ASCII -> {bits} bits with Huffman")

js = '[{"id":1,"ok":true},{"id":2,"ok":true}]'
print("\nLZ77 on", js)
for tok in lz77(js):
    if tok[0] == "copy":
        print(f"  copy {tok[1]} chars from {tok[2]} back")
print(f"{len(js)} bytes -> zlib level 9: {len(zlib.compress(js.encode(), 9))} bytes (header and checksum included)")

Toy vs production

Every operation on this page is the real one. What changes at scale is how far the window reaches, how hard the compressor searches, and how the trees are chosen.

This pageReal DEFLATE, and after
windowa few characters32 KB in DEFLATE. Brotli reaches 16 MB and ships a built-in dictionary of common web text; zstd can use windows of hundreds of megabytes.
finding matchescompare against every earlier positionHash tables and chains. Levels 1 to 9 control how long the search is allowed to take, not how big the window is; level 9 rarely beats level 6 by more than a percent.
treesone tree, or the fixed onesCustom trees per block, sent as canonical code lengths (Example 6), those lengths themselves Huffman-coded. A new block whenever the statistics change.
limitsnoneCopy length 3 to 258, distance 1 to 32,768. Bigger lengths become several copies.
speedirrelevantDecompression is several times faster than compression: copying is cheap, searching is not. That asymmetry is why it is fine to compress once and serve a million times.
what will not shrinkABRACADABRA shrinks a lotAlready-compressed data: JPEG, MP4, another zip. Their entropy is near 8 bits per byte (Example 4). 10,000 random bytes gzip to 10,023.
tiny inputs11 bytes became 29Wrappers have fixed cost. Servers set a minimum response size for gzip, and protocols like HTTP/2 compress headers with a different scheme built for small strings.
successorsDEFLATEBrotli (RFC 7932) and zstd (RFC 8878) use the same two tricks with bigger windows, smarter entropy coding and dictionaries. Browsers accept all three: Accept-Encoding: gzip, br, zstd.

gzip turned the 39-byte JSON from Example 5 into 46 bytes. Where did the extra 7 come from?

The DEFLATE stream itself is 28 bytes, an 11-byte saving. Then gzip adds its 10-byte header and 8-byte trailer, 18 bytes in total, and 28 + 18 = 46. The same stream inside zlib's smaller 6-byte wrapper is 34 bytes. Below a few dozen bytes, the wrapper is the whole story.

Why does zipping a folder of JPEGs barely change its size?

JPEG has already spent its own compression step removing the patterns. What is left has entropy close to 8 bits per byte, so by Example 4 there is nothing for Huffman to save, and there are no long repeats for LZ77 to point at. You get the zip headers added and little else. The same goes for MP4, PNG, and another zip.
