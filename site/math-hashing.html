Hashing and the birthday paradox

One function turns anything into a fixed-size number that looks random. One party trick from probability tells you exactly when two of those numbers will clash. Together they are hash maps, git, UUIDs, password storage, and the reason seven-character commit IDs stopped being enough.

Plain text is theory. Boxed examples: problem, working, answer.

Where you meet it

You called a hash function before you finished reading this sentence. Probably several.

Every dictionary and cache

A Python dict, a Java HashMap, a Redis key. Hash the key, jump to a bucket, compare once. Example 1 does it with 8 buckets and a pencil.

Every git commit

A commit's name is the hash of its content, and 587b699-style short IDs are the first 7 characters. Example 5 computes when those start colliding, and why the Linux kernel asks for 12.

Every ID you mint

UUIDs are 122 random bits. Snowflake IDs are a timestamp, a machine number and a counter packed into 64 bits. Example 6 decodes one and puts a number on "will they collide".

Every password and every download

Passwords are stored as slow hashes on purpose. Docker layers, ETags and package downloads are named by their hash so nothing can change unnoticed. Examples 7 and 8.

The idea in one breath

A hash function takes input of any size and returns a number of fixed size. Same input, same number, every time. Change one bit of the input and the whole number changes. A good one cannot be run backwards.

That buys two things. Placing: hash mod buckets says which drawer a key lives in, so finding it is one step whether the table holds ten keys or ten million. Naming: the hash is the name of the content, which is how git, Docker and your browser cache know two things are identical without comparing them byte by byte.

The one thing that can go wrong is a collision: two inputs, one number. The birthday paradox says collisions arrive after roughly the square root of the number of possible outputs, which is far sooner than intuition expects. Every number on this page is that square root, applied.

Placing: a hash map by hand

A hash map is an array of buckets plus a rule for choosing one. To store a key, hash it, take the result mod the number of buckets, and drop the key in that bucket. To find it, do the same computation and look in the same place. If two keys land in one bucket, keep both in a short list and compare against each. We will use a deliberately simple hash: add up the letter positions, A = 1 to Z = 26.

The birthday paradox

How many people must be in a room before it is more likely than not that two share a birthday? Most people guess somewhere near 180. The answer is 23. Tool 3 does the counting: the chance that nobody shares is a chain of "avoids everyone before them" fractions, and flipping it gives the chance that someone does.

The square-root rule

Now swap birthdays for hash values. A hash with N possible outputs is a year with N days. Items are people. The pairs argument from Example 3 says n items make about n²/2 pairs, each colliding with chance 1/N, so the expected number of collisions is n²/(2N), and the chance of at least one is 1 − e−n²/2N. Set that to 50% and solve: n = √(2 ln 2 · N) ≈ 1.18 √N.

A hash of b bits is safe for about 2b/2 items. Halve the bits in your head and that is your budget. A 32-bit hash is a fine checksum for catching accidental corruption and a terrible choice for naming 100,000 things.

Naming: git's seven characters

git names every commit, file and tree by the SHA-1 of its content, 40 hex characters. Nobody types 40 characters, so git shows a prefix, historically 7. Seven hex characters is 28 bits, and Example 4 tells you what happens next.

The 3% in this repository is the chance that a 7-character ID written down today stops being unique as commits are added.

Naming: the IDs you mint

There are two ways to hand out IDs without a central counter. Make them random and huge, so collisions are possible but absurdly unlikely: that is a UUID. Or make them structured, packing a timestamp, a machine number and a counter into the bits, so collisions are impossible by construction: that is a Snowflake ID, the scheme Twitter published in 2010 and half the industry copied.

Break a hash on your laptop

The square-root rule is also the attacker's rule. Finding two inputs with the same hash is called a birthday attack, and it needs about 2b/2 tries. Watch it succeed on a hash shortened to 16 bits, then compute why the same attack on a full SHA-256 outlives the universe.

Example 7

Sixteen bits fell in 172 tries, right where the square-root rule said. The full 256 bits would take a billion times the age of the universe. That gap is the entire difference between a checksum and a cryptographic hash. SHA-1's budget was 2⁸⁰ on paper; researchers found a shortcut to 2⁶³ and produced a real collision in 2017, which is why git is moving to SHA-256.

Passwords: a hash that is slow on purpose

A server never stores your password, only a hash of it, so a stolen database does not give the passwords away. But an attacker with the database can guess: hash "password123", compare, repeat. Fast hashes make guessing fast. Password hashes such as PBKDF2, bcrypt and Argon2 are built to be slow, and to be mixed with a random salt per user so identical passwords hash differently and precomputed tables are useless.

Example 8

The cost of 10 million guesses

Measured on this laptop in Python: one plain SHA-256 takes 0.3 microseconds. One PBKDF2-HMAC-SHA256 with 600,000 rounds, the count OWASP recommends, takes 0.29 seconds. Compare an attacker's bill for 10 million guesses against one user's login.

The same hash function, made a million times more expensive, turns a 3-second attack into a month per user while costing the real user a blink. Whatever hardware the attacker brings, the ratio holds. Never store passwords with a fast hash, and never without a salt.

Run it

Build it: every example in forty lines

Standard library only. The birthday attack in the middle finds its collision in well under a second.

# Hashing and the birthday paradox, with numbers small enough to check on paper.
# Companion to math-hashing.html. Python 3 standard library only.
import hashlib, math, os, time

def toy_hash(word):
    """Sum of letter positions, A=1 ... Z=26. Deliberately weak: anagrams collide."""
    return sum(ord(c) - 64 for c in word)

buckets = [[] for _ in range(8)]
for word in ["CAT", "DOG", "COW", "HEN", "ACT"]:
    buckets[toy_hash(word) % 8].append(word)
print("buckets", buckets)

def java_hash(s):
    """Java's String.hashCode: h = 31*h + c, kept to 32 bits."""
    h = 0
    for c in s:
        h = (31 * h + ord(c)) & 0xFFFFFFFF
    return h
print("java CAT", java_hash("CAT"), "ACT", java_hash("ACT"))

p_none = 1.0
for person in range(1, 24):
    p_none *= (365 - (person - 1)) / 365
print(f"23 people: P(shared birthday) = {1 - p_none:.4f}")

def n_for_50_percent(bits):
    return math.sqrt(2 * math.log(2) * 2 ** bits)
for bits in (16, 28, 32, 64, 122, 256):
    print(f"{bits:3d}-bit hash: 50% collision after {n_for_50_percent(bits):.3g} items")

seen = {}
for i in range(1_000_000):
    s = f"msg-{i}"
    prefix = hashlib.sha256(s.encode()).hexdigest()[:4]
    if prefix in seen:
        print(f"collision after {i + 1} strings: {seen[prefix]} and {s} both hash to {prefix}...")
        break
    seen[prefix] = s

salt = os.urandom(16)
t0 = time.perf_counter()
hashlib.pbkdf2_hmac("sha256", b"correct horse", salt, 600_000)
slow = time.perf_counter() - t0
t0 = time.perf_counter()
for i in range(100_000):
    hashlib.sha256(b"correct horse").digest()
fast = (time.perf_counter() - t0) / 100_000
print(f"one guess: plain sha256 {fast * 1e6:.1f} us, pbkdf2 600k rounds {slow:.2f} s, ratio {slow / fast:,.0f}x")
print(f"10 million guesses: {1e7 * fast:.0f} s plain, {1e7 * slow / 86400:.0f} days with pbkdf2")

Python randomises its string hash with a fresh secret key every time the interpreter starts. In 2011 researchers showed that a web server could be stalled by sending it a few thousand form fields crafted to land in the same bucket, turning every lookup into a walk down one enormous list. A secret per process means an attacker cannot know which keys collide. Note the third digit of the UUID's third group: it is always 4, one of the six fixed bits from Example 6.

Toy vs production

Every operation on this page is the real one. What changes is which hash function does which job, and how tables and IDs are engineered around collisions.

This pageReal systems
the functionletters added up; Java's ×31One function per job. SipHash for hash tables (fast, keyed, hard to flood). MurmurHash and xxHash for speed. SHA-256 when an adversary is involved. PBKDF2, bcrypt or Argon2 for passwords.
collisions in a tablea short list per bucketPython's dict probes the next slot instead (open addressing); Java's HashMap chains and turns a long chain into a tree. Both grow the table when it is about two-thirds full so lookups stay one or two steps.
attackersnoneHash flooding, 2011: crafted keys all in one bucket, quadratic slowdowns, stalled servers. Fixed with a per-process secret key, which is why Python's hash('abc') changes every run.
naming contentgit's 7 charactersgit is moving from SHA-1 to SHA-256. Docker layers are sha256:… digests. Browsers cache by ETag, package managers verify downloads by hash. Same bytes, same name, no central registry.
IDsone UUID, one SnowflakeUUID v4 for randomness, Snowflake-style for time-sortable IDs, UUID v7 (RFC 9562, 2024) for both. Databases prefer time-ordered IDs because random ones scatter inserts across the whole index.
"broken"4 hex digits in 172 triesMD5 collides in seconds, SHA-1 in 2⁶³ work (2017). Both remain fine as checksums against accidents. Neither may be used where someone might want a collision.

Two users choose the password "hunter2". Do they end up with the same hash in the database?

Only if the system is broken. Each user gets a random salt, and the salt is mixed into the hash, so the stored values differ. Without salts, identical passwords would be visible as identical hashes (the same way H was always 17 in the RSA chapter), and an attacker could hash a list of common passwords once and compare it against every account at the same time.
